# Pipeline Implementation Plan (plan 3 of 5)

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Make Jenkins run the branch policy, every Linux check and the releases (deploy-driven and
owner-tagged, library packages included) for repositories on Forgejo or GitHub, report results to the git
server, use GitHub Actions only for Windows/macOS jobs (with the skip), and run Renovate.

**Architecture:** Decisions live in small tested scripts; the Groovy library only orchestrates them.
`scripts/pipeline_config.py` reads and validates each repository's `yggdrasil.yml` (data, no code) against
the catalog and plans which checks run, are reused or skipped. `scripts/branch-policy.sh`,
`scripts/run-check.sh`, `scripts/release_notes.py` and `scripts/publish-release.sh` do one job each, on top
of plan 2's `forge.sh`, and `github.sh` gains the Actions commands. Jenkins builds every branch, pull request
and tag with **one Jenkinsfile kept in Jenkins** (not in the repository), which calls the pinned
`yggdrasilPipeline`; a gated live suite runs the real controller, a CI agent and Forgejo in containers.

**Tech Stack:** Bash, curl, jq; Python 3.10+ (stdlib + PyYAML); Jenkins (Configuration as Code, Job DSL,
Gitea plugin, Pipeline: Multibranch with defaults, HTTP Request, JUnit); Groovy (scripted pipeline);
Docker; Forgejo 16.0.6; Renovate (container); unittest.

**Spec:** `docs/superpowers/specs/2026-10-22-self-hosted-git-and-ci-design.md` — "GitHub Actions: only Windows and
macOS", "CI in Jenkins", "Releases", "Owner-tagged releases", "Renovate", "Libraries", "Sites" (what the
pipeline gives them), "Implementation plans" item 3.

**Not in this plan:** each repository's `yggdrasil.yml`, `ci/` scripts and trimmed `.github/workflows` (plan 5);
building the machines, accounts, cutover (plan 4); sites' stack files and the status API showing full host names
(plan 5). Renovate's runner is here although the spec's plan list doesn't name it: it is yggdrasil code (rollout
step 1), and plan 4 only turns it on.

## Decisions this plan makes (read first)

1. **The Jenkinsfile is not read from the repository** (deviation from the spec's "declared in its Jenkinsfile";
   for the owner to confirm). Jenkins plugins treat a pull request from a branch of the repository itself as
   trusted, so a branch pushed by `claude` would run its own Jenkinsfile, with every Jenkins credential in reach —
   the spec's "target branch's Jenkinsfile" rule can't be expressed for such pull requests, and a library-side
   refusal is bypassed by a Jenkinsfile that doesn't call the library. Instead every job uses one script stored in
   Jenkins (`@Library('yggdrasil') _` + `yggdrasilPipeline()`), and each repository describes its checks and
   releases in **`yggdrasil.yml`** at its root: data only (images, commands of `ci/` scripts, globs, credential
   *names*). Commands run only on the isolated CI agent or, for releases the owner started, on the release agent;
   credentials only from the catalog's allow-list. The spec's intent (steps in the repository; only the owner
   changes pipelines) holds; plan 2's protected `Jenkinsfile` becomes moot, and nothing else changes.
2. **Statuses are posted from the controller** with the HTTP Request plugin's `httpRequest`, outside `node()`, by
   one Groovy helper; if the live suite shows it can't run there with a masked token, the helper posts from the
   publish agent instead (one place to change).
3. **The publish agent** (merge, tag, release, uploads; it holds the `jenkins` write token and the GitHub App) is
   new catalog field `forge.publishAgent`, default: the agent of the last release environment in catalog order
   (the agent that merges and releases today).
4. **Reuse by commit trusts only statuses whose creator is `forge.jenkinsUser`** — any write user can post a
   status.

## Global Constraints

- Two git servers via `forge.type`; with no `forge` block, GitHub, and a repository without `yggdrasil.yml`
  behaves exactly as today (deploys only; on a release, waits for every GitHub Actions check).
- The CI agent (`ci`, 4 executors) and release agent (`release`, 1 executor) never hold a write credential:
  checkout with `forge-read`; statuses, merges, tags, releases and uploads elsewhere (decisions 2–3).
- `yggdrasil.yml` fields: `checks` (name → `image`, `run`, `docker`, `credentials`, `paths`, `junit`, `archive`),
  `branchPolicy` (`image`, `run`), `deploy.inputs` (check names whose archives go into the image build),
  `release` (`build` {`image`, `run`, `files`, `credentials`}, `windows` {`workflow`, `files`}, `validate`
  {`image`, `run`}), `publish.nuget` (`image`, `run`, `packages`). Unknown keys are errors.
- Credentials: only ids the catalog allows the repository (`credentials` of the application or repositories
  entry); never bound on `renovate/*` builds.
- Branch policy: into `develop` only `feature/*`, `fix/*`, `renovate/*` (not `dependabot/*` any more), not cut from
  `main`; into `main` only `release/x.y.z`, an unchanged snapshot of `develop`, untagged version.
- Statuses: `pending` then `success`/`failure`, target the build URL; contexts are the check names; reuse never
  applies to `branch-policy`.
- GitHub Actions: `wait` exit codes `0` passed, `1` a check failed, `2` timed out / GitHub didn't answer / the
  mirror hasn't the commit; waiting never holds an executor.
- The skip (release pull requests only, exit 2): input "GitHub Actions checks didn't finish. Deploy without
  them?", button **Deploy without GitHub Actions checks**, outside `node()`; recorded in the build log, the build
  description (`v1.4.0 (deployed without GitHub Actions checks)`) and the `deploy/<environment>` descriptions;
  Windows files missing → release published without them, build **unstable**, missing files listed.
- Releases: tag and **draft** Forgejo release; files built/signed on the release agent, Windows files from the
  GitHub workflow (`workflow_dispatch` once the tag reached GitHub); validation on the release agent; uploads to
  both drafts by the publish agent, checked; publish Forgejo, then GitHub last. Release notes: the version's
  `CHANGELOG.md` section, else merged pull request titles since the previous tag.
- `delete-branch` exit 3 (kept, protected) is success with a note.
- Owner-tagged repositories: a tag build checks the tag's commit is on `main`, then releases (files) or publishes
  (NuGet, key only on the release agent's publish step).
- Library version pinned: `YGGDRASIL_LIBRARY_VERSION` (a yggdrasil release tag) required with profile `jenkins`.
- Renovate: user `renovate`, its own rootless engine, systemd user timer daily, `renovate/*` branches.
- Tests: WSL `python3 -m unittest discover -s scripts -p <file>`; live suites gated (`YGG_FORGEJO_TESTS=1`,
  `YGG_JENKINS_TESTS=1`); shellcheck silent; names `test_given_…_when_…_then_…`; commits lowercase Conventional,
  ≤50 chars.

## Review Focus

1. **A non-owner's branch reaching a credential**: a `claude` branch with a Jenkinsfile, a `yggdrasil.yml`
   naming a credential the catalog doesn't allow, or a `renovate/*` build (Tasks 2, 8, 9, 10 tests).
2. **A forged status skipping a check**: a `success` posted by a user other than `jenkinsUser` must not be
   reused (Task 3 test; live in Task 10).
3. **GitHub slow or down**: the mirror not yet having the commit, GitHub 5xx, a workflow never starting —
   waits end in exit 2 and the skip, never a hung build or a held executor (Tasks 5, 11 tests).
4. **A release half done**: a failing upload or validation leaves both drafts unpublished and fails the build; a
   re-run of the same release picks up the existing tag/drafts instead of failing on "already exists"
   (Tasks 6, 11 tests).
5. **A repository with no `yggdrasil.yml`** (every repository of an existing GitHub installation, and each
   repository here until plan 5 moves it): no checks, no branch policy, deploys and releases as before
   (Task 2 test of `describe` with no file; Task 10 live test of a push that only deploys).

- Flow (spec "Pipeline flow" table), all with `pipeline_config.py describe` first (on `node('ci')`, checkout with
  `forge-read`):
  - **No `yggdrasil.yml`**: exactly today's behavior (deploys; release pull request: today's wait for every Actions
    check via `github.sh wait-checks`, today's release path).
  - **Pull request into `develop`/`main`**: stage *Branch policy* (`branch-policy.sh`, then `branchPolicy`'s extra
    via `run-check.sh`; status `branch-policy`); stage *Checks*: `get-statuses` + changed files (`git diff --name-only
    origin/<target>...HEAD`), `plan`, then in `parallel` one branch per planned check on `node('ci')`: `run` →
    `run-check.sh`, `junit`/`archive` collected, the archive also `stash`ed as `check-<name>`; `reuse`/`skip` → only a
    status with the reason. Statuses through one helper `reportStatus(repo, sha, state, context, description)`
    (decision 2). The build fails after all checks reported if any failed.
  - **Pull request into `develop` (Forgejo, `actionsChecks` set)**: after the checks, outside `node()`, a loop of
    `node('ci') { github.sh actions-status … }` every 60 s until exit 0/1 or `checksTimeout`; each named check copied
    to Forgejo (`reportStatus`, target the GitHub run URL); on exit 2/timeout they are set `pending`, "GitHub Actions
    didn't answer", and the build ends unstable.
  - **Push to `develop`/`main`/`release/*`**: the checks (changed files against the previous successful build's
    commit, else all run), then the branch deploys only if green; `deploy.inputs` are unstashed into a directory
    given as `DEPLOY_INPUTS_DIR`.
  - Credentials bound per check with `withCredentials` only for ids the describe step returned (decision 1), written
    to a 600 env file for `run-check.sh`, removed afterwards.

  - Scripts run from the yggdrasil checkout next to the application's; `YGG_GITHUB_SH` (agent environment, set
